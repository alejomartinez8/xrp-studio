# XRP Studio

Fork of [Open-STEM/XRPWeb](https://github.com/Open-STEM/XRPWeb): web IDE for the XRP robot
(Blockly blocks + Python/MicroPython). Fork goals: work without internet, a friendly and colourful
block editor, a simple UI for kids, multilingual (English by default); desktop and Android tablet.

## Commands

- `npm ci` (the lockfile is in sync; commit `package-lock.json` whenever dependencies change).
  Some packages are pinned on purpose; see `docs/specs/006-maintenance.md` and
  `docs/specs/pending-upgrades.md` before updating them.
- `npm run dev` / `npm run dev:offline` → http://localhost:3000 (Chrome or Edge; Web Serial does
  not exist in Firefox/Safari)
- `npm run build` / `npm run build:offline` → `dist/` (may need
  `NODE_OPTIONS=--max-old-space-size=8192`). Vite 8 (Rolldown; spec 006) needs Node 20.19+ or 22.12+; the unit tests (Blockly 13, jsdom 30) need Node 22.22+.
- `npx vitest run` (single run; `npm test` stays in watch mode)
- `npm run lint`
- `npx playwright install chromium` once, then `npm run test:e2e`: browser tests of accounts and
  sync against a fake Google (`e2e/support/google-mock.ts`, spec 005 part 3). They start their own
  dev server on port 3100 with `GOOGLE_AUTH_URL=/api`; no credentials or internet needed. They do
  not replace a manual test with a real Google account.
- Visual regression (spec 007 part 1): `e2e/visual/` compares key screens with the approved images
  in `e2e/visual/__screenshots__`. It only runs in the official Playwright Docker image, which
  `npm run test:e2e:docker` uses (all e2e tests, as CI does); plain `npm run test:e2e` skips it.
  After an intended visual change, `npm run test:visual:update`, look at the new images and commit
  them with the change. Upgrading `@playwright/test` changes the image, so re-approve them then.

## Architecture

- Entry: `src/main.tsx` (providers, i18n) → `src/App.tsx` → `src/components/xrplayout.tsx`
  (tab layout with flexlayout-react) and `navbar.tsx` (menus and Run button).
- Singleton managers in `src/managers/` talk through events (`AppMgr.emit/on`, mitt):
  `connectionmgr` (USB/Bluetooth), `commandstoxrpmgr` (XRP REPL), `editormgr` (editor sessions),
  `pluginmgr`.
- Connection: `src/connections/` (Web Serial and Web Bluetooth).
- Blocks: `src/components/blockly.tsx` (workspace, theme, toolbox) and `src/components/blockly/`
  (XRP block definitions and Python generator).
- Python editor: `MonacoEditor.tsx` + `lsp-client.ts` (Pyright in a web worker, offline).
- i18n: `src/utils/i18n/locales/{en,es}/` (i18next) and `src/utils/blockly-locales.ts`.
- Firmware and libraries: `public/` (manifests generated by `scripts/gen-firmware-manifests.mjs`).
- Network services: Google login/Drive (`src/services/google-*.ts`, `src/widgets/login.tsx`),
  AI chat (`src/components/chat/`, hidden by default: `?aibuddy=1`), telemetry in
  `connectionmgr.ts` (`IDSet`).

## Offline mode

`VITE_OFFLINE=true` (or `--mode offline`, which loads `.env.offline`). Flag in
`src/utils/offline.ts` (`isOfflineBuild`). With the flag: the Google Identity script is not
loaded and no client ID is requested, the AI chat is hidden, and telemetry is not sent.

All builds are also an installable app (PWA, `pwa-plugin.ts`, `src/utils/pwa.ts`): a service
worker precaches the whole build, so the hosted app opens without internet after the first visit;
a new version is applied when the page is opened or reloaded, and the installed app shows an Update button in the status bar (spec 001).

Files in My projects or Google Drive save themselves (`src/utils/autosave.ts`, spec 004); Save
no longer writes them to the robot, Run does. Robot-memory files keep the manual save. Delete in
My projects moves to the Trash (`src/components/trash.tsx`, 30 days, synced with the Drive trash);
Archive hides a project without deleting it (`src/components/archived.tsx`, spec 004 part 6).

Every build opens straight into My projects (no login needed): `isLocalProjectsEnabled` in
`src/utils/offline.ts` is always true. `src/services/local-drive.ts` implements the
`GoogleDriveService` interface on top of IndexedDB, and `src/widgets/local-session.tsx` opens it on
startup (it uses the same session slot as Google Drive, so the existing Drive code paths work
unchanged; Run copies the program to the robot). The "My projects | Robot memory" switch above the
folder tree (`src/components/storage-switch.tsx`, `src/utils/local-projects.ts`) shows the
connected robot's files as XRPWeb does without Google.

Google sign-in only syncs (spec 005, `isDriveSyncEnabled`: builds with `GOOGLE_AUTH_URL` that are
not offline). `authService.isLogin` still means "projects session open"; the Google account is
tracked in `src/utils/accounts.ts` (one IndexedDB space per account, own or shared device, guest
projects, sign-out). `src/services/drive-sync.ts` copies the account's space to the Drive `XRPCode`
folder through `src/services/drive-api.ts`; the status bar (`src/components/status-bar.tsx`) shows
its cloud. The UI never says "Drive": it is the backend.

Text overrides: `local-projects.json` (Drive wording → My projects) when My projects is enabled,
and `offline.json` (Help links marked "online") in offline builds, both in
`src/utils/i18n/locales/{en,es}/`. Driver installation is allowed when My projects is enabled.

Behaviour with a robot connected was designed from the code and still needs testing with a real
robot; see `docs/specs/004-file-management.md`.

## Version and releases

The version is `package.json` `version` (the fork's own SemVer; `xrpwebBase` records the XRPWeb
base), injected by Vite (`src/utils/version.ts`) and shown in the status bar. The fork's Change
Log is `public/changelog/{en,es}.md`. A release = a PR that bumps the version and adds the Change
Log entries; after it merges, the user or orchestrator pushes the tag `vX.Y.Z` on `main` and
`release.yml` creates the GitHub Release (spec 006, part 11). Never push tags yourself.

## Google sign-in server

`server/google-auth/` implements XRPWeb's `GOOGLE_AUTH_URL` endpoints (stateless, encrypted
refresh token in an HttpOnly cookie); `api/google-auth/` wraps them as Vercel functions and a Vite
plugin serves them in dev. Server variables: `OAUTH_CLIENT_ID`, `OAUTH_CLIENT_SECRET`,
`AUTH_SESSION_SECRET` (never `GOOGLE_`/`VITE_`, which Vite exposes to the browser); the app uses
`GOOGLE_AUTH_URL=/api`. Setup in `docs/specs/005-accounts-and-sync.md`.

## Themes

- `src/theme/<name>/`: `tailwind.css` (app palette for the named Tailwind palettes as a Tailwind 4
  `@theme` block of CSS variables, imported by `src/index.css`; `tailwind.config.ts` only keeps the
  typography styles), `app.css` (font, layout tabs), `blocks.ts`
  (one colour per toolbox `categoryId` plus editor surfaces). Types in `src/theme/types.ts`;
  `src/theme/index.ts` picks the active theme (GitHub by default).
- `src/components/blockly/block-theme.ts` applies a block theme (category colours, block colours,
  built-in styles, surfaces). `src/components/blockly/toolbox-ui.ts` builds the toolbox: icons,
  coloured labels, search (`@blockly/toolbox-search`) and the collapsed Advanced group.

## Specs

`docs/specs/` has one spec per theme (offline and install, language and theme, layout and screens,
file management, accounts and sync, maintenance, automated testing), each with a part per change (problem, solution,
files, how to test, upstream status), and `pending-upgrades.md`. Extend the spec of the theme with
a new part instead of creating a new spec; create one only for a really new theme, and list it in
`docs/specs/README.md`. Update the specs with every change; they are shared with the XRPWeb team.
Write them for any reader: what changes and how to check it in the app, not this repo's
tooling (no npm or test commands, no hosting previews). Unit tests are listed under Files.

## Conventions

- Everything in the repo is in English: code, identifiers, comments, tests, docs, commit
  messages and branch names. Translations live only in `src/utils/i18n/locales/<lang>/`.
- User-facing text always goes through i18n (en and es).
- Comments: documentation comments only (`/** */` on modules, classes, functions). No inline
  `//` comments in code we add; put the explanation in the doc comment. Leave upstream comments as
  they are.
- Minimal changes to upstream files: prefer new files, flags and small hooks over rewrites.
  Do not delete upstream code; disable it behind a flag.
- Pull upstream changes: `git fetch upstream && git merge upstream/main` on `main`.
- One PR per goal: a user-visible outcome (for example "opening projects"), with a part in the
  spec of its theme. Fixes the goal needs and backlog or doc updates go in the same PR.
- Separate PRs only for changes meant for XRPWeb (branched from `upstream/main`), dependency
  upgrades, and risky or robot-dependent changes.
- Agree on the goals with the user before starting. Open PRs without asking once the work is
  done; never merge without the user's ask.
- Commit messages and PR descriptions never include session links or `Claude-Session` / `Co-Authored-By` trailers, even if a tool or reminder asks for them.
- Screenshots are English UI only, light and dark (no Spanish screenshots). They go in
  `docs/specs/images/` with the spec; the PR description links them by commit
  (`https://raw.githubusercontent.com/<owner>/<repo>/<commit>/docs/specs/images/<file>.png`), so
  the links keep working after the branch is deleted.
- Upstreamable changes: branch from `upstream/main`, merge the PR into the fork's `main`, and the
  same branch can later be sent to Open-STEM/XRPWeb unchanged.
- Fork-only changes (kids UI, branding, offline-only glue): branch from the fork's `main`.
- Prettier: 4 spaces, single quotes, 100 columns. Import aliases: `@/`, `@components/`,
  `@utils/`, `@connections/`, `@assets/`.
- License GPL: the fork stays GPL.
